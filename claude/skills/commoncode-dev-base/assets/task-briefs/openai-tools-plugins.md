# Инструкция для AI-агента: Создание прототипа тестирования OpenAI-совместимого Tools-режима (Lesson_X)

## Общая задача
Спроектируйте и реализуйте новое учебное приложение в директории `lesson_X` (где `X` — следующий доступный порядковый номер урока, получаемый списком текущих папок и увеличением на один). **Приложение не должно читать код из существующих lesson-папок.**

Приложение — технологический прототип для:
1.  Проверки работоспособности **Tools-режима** (function calling) через OpenAI-совместимое API на примере сервисов OpenRouter (модель DeepSeek) и LM Studio (модель Qwen 3.5 9B).
2.  Демонстрации паттерна **Tool = Plugin**, где каждый инструмент реализован как отдельный плагин в папке `tools/plugins/`, а приложение динамически загружает их схемы и функции-обработчики.

Приложение учебное, демонстрирует архитектурные стандарты: изоляция слоёв, Agentic UX, Headless-тестирование, LDD (Log-Driven Development).

**КРИТИЧЕСКОЕ ПРАВИЛО ОКРУЖЕНИЯ:** Запрещается создавать новые виртуальные окружения (VENV) и переустанавливать библиотеки, если они уже присутствуют в системе. Изоляция достигается исключительно инкапсуляцией файлов внутри `lesson_X/`.

**ИСКЛЮЧЕНИЕ — установка openai:** Если библиотека `openai` (>= 1.0.0) отсутствует в системе, её необходимо установить одной командой: `pip install "openai>=1.0.0"`. Это единственное исключение из правила запрета установки.

## Бизнес-требования и функциональность

### 1. Плагинная архитектура инструментов
- Каждый инструмент реализуется как отдельный Python-файл в папке `tools/plugins/`.
- Плагин должен экспортировать:
  - `TOOL_SCHEMA` — словарь с JSON-схемой в формате OpenAI Function Calling.
  - `run(**kwargs)` — функция-обработчик, принимающая аргументы из JSON-схемы инструмента (как именованные параметры). `tool_executor` (контроллер-диспетчер плагинов) передаётся отдельно, через замыкание или декоратор, но не через сигнатуру `run()`.
- При старте приложение сканирует папку `tools/plugins/`, загружает все плагины и формирует список инструментов для отправки LLM.
- **Для прототипа run-функции не выполняют реальной работы (нет БД). Они только пишут информационное сообщение в лог-файл `lesson_X/app_X.log` с уровнем INFO, содержащее название инструмента и переданные аргументы.**
- Именование файлов плагинов: по имени инструмента (из `TOOL_SCHEMA`), латиницей. Например: `test_no_params.py`, `test_simple_params.py`, `test_optional_params.py`, `test_array_of_strings.py`, `test_array_of_objects.py`, `test_nested_object.py`.

### 2. Конфигурация подключений (State Management)
- Приложение использует единый файл `config.json` (внутри `lesson_X/`) для хранения **несекретных** параметров подключения к LLM-бэкендам.
- **Ключи API НИКОГДА НЕ ХРАНЯТСЯ** ни в `config.json`, ни в каком-либо другом файле внутри `lesson_X/`. Пользователь передаёт ключ только через аргумент командной строки или переменную окружения.
- Структура `config.json`:
  - `active_profile: str` — имя активного профиля (совпадает с `name` одного из профилей).
  - `profiles: [...]` — массив профилей подключения. Каждый профиль:
    - `name` (например, `"deepseek"`, `"qwen_local"`)
    - `base_url` (эндпоинт API)
    - `model` (название модели)
    - `temperature`, `max_tokens` и другие параметры.
- Пример `config.json`:
  ```json
  {
    "active_profile": "deepseek",
    "profiles": [
      {
        "name": "deepseek",
        "base_url": "https://api.deepseek.com",
        "model": "deepseek-v4-flash",
        "temperature": 0.7,
        "max_tokens": 4096
      },
      {
        "name": "qwen_local",
        "base_url": "http://localhost:1234/v1",
        "model": "qwen-3.5-9b-instruct",
        "temperature": 0.5,
        "max_tokens": 2048
      }
    ]
  }
  ```
- **Без активного ключа** приложение не должно выполнять запросы к API.

### 3. Основной рабочий процесс (MVP Runner)
Единственная точка входа — `lesson_X/run_mvp.py`. Корневой `run_lesson_X.py` не создаётся.

**API KEY SECURITY (CRITICAL):** Ключ API НИКОГДА не должен быть записан ни в один файл внутри `lesson_X/` (ни в `config.json`, ни в `.env`, ни в любой другой файл). Единственные источники: `--api-key` CLI arg, переменные окружения. Это защищает от случайного коммита ключа в репозиторий.

Приложение предоставляет консольный скрипт `run_mvp.py`, который:
1.  Принимает API-ключ (аргумент командной строки `--api-key` → переменная окружения `OPENROUTER_API_KEY` → `LLM_API_KEY`). Если ключ не найден нигде — завершается с ошибкой.
2.  Загружает конфигурацию из `config.json` и получает параметры активного профиля.
3.  Сканирует `tools/plugins/`, загружает `TOOL_SCHEMA` и `run` из каждого плагина.
4.  Формирует запрос в формате OpenAI Chat Completions API (роль `user` с тестовым сообщением, массивом `tools` из схем).
5.  Отправляет запрос к указанному `base_url` с использованием стандартной библиотеки `openai` (OpenAI Python SDK >= 1.0.0, которое умеет передавать `base_url`).
6.  Принимает ответ, извлекает `tool_calls` (если модель решила вызвать инструменты).
7.  Для каждого `tool_calls`:
    - Находит соответствующий плагин.
    - Вызывает его `run()` с аргументами, полученными из JSON-аргументов вызова.
    - Логирует результат вызова.
8.  Выводит в консоль сводку: какие инструменты были вызваны и с какими аргументами.
9.  Завершается (single-shot, без интерактивного цикла).

### 4. Декларации инструментов (Tools)
Используйте **ровно 6 инструментов**, покрывающих различные паттерны параметров (см. Приложение А). JSON-схемы уже готовы, их нужно встроить в соответствующие файлы плагинов.

### 5. Логирование (LDD 2.0)
- Все логи пишутся в файл `lesson_X/app_X.log`.
- Используется уровень логирования INFO и WARNING.
- Применяется маркировка `[IMP:1-10]` в логах.
- В критических точках (загрузка плагинов, отправка запроса, получение ответа, вызов run) фиксировать "AI Belief State" (что система ожидает, что фактически произошло).
- `tool_executor` логирует каждый вызов плагина с `[IMP:8-9]`, включая имя инструмента, полученные аргументы и результат.

## Требования к разработке и архитектуре
1.  **Соблюдение фреймворка промптов:** Весь код оборачивается в "Семантический Экзоскелет" (регионы `# region MODULE_CONTRACT` / `# endregion` с KEYWORDS, Doxygen-теги `## @purpose`, `GREP_SUMMARY`, `STRUCTURE`). **Используется Doxygen-стиль** (как в `lesson_x`), НЕ старый формат `# START_MODULE_CONTRACT:`. Контракты пишутся в парадигме "Zero-Context Survival". Если фреймворк недоступен, остановить работу и сообщить об ошибке настройки агентской среды.
2.  **Изоляция слоёв:** Конфигурация, плагины, клиент API и runner разделены по модулям.
3.  **Headless-тестирование:** Никакого UI (Gradio) не требуется. Тестирование полностью консольное через `pytest`.

## Стратегия тестирования (100% покрытие бизнес-логики в `lesson_X/tests/`)
Реализуйте тесты на `pytest` с обязательным `conftest.py` (Anti-Loop Protocol). Тесты должны проверять:

1.  **Тесты отдельных плагинов:** Для каждого из 6 инструментов — атомарный тест, проверяющий:
    - Корректность `TOOL_SCHEMA` (наличие обязательных полей, правильные типы).
    - Вызов `run()` с валидными аргументами и проверка, что функция логирует ожидаемое сообщение.
    - Поведение при невалидных аргументах (если в плагине предусмотрена валидация).
2.  **Интеграционный тест полного цикла:**
    - Имитация запроса к API с замоканным HTTP-ответом (чтобы не делать реальных запросов). Использовать `unittest.mock.patch` на уровне клиента `openai.OpenAI.chat.completions.create`.
    - Мок должен возвращать корректный JSON с `tool_calls`.
    - Проверка, что система правильно парсит ответ, вызывает нужные плагины и логирует вызов.
3.  **Тест конфигурации:** Проверка загрузки `config.json` и переключения активного профиля.
4.  **Тест безопасности:** Проверка, что `config.json` НЕ содержит поля с API-ключом (защита от случайной записи).
5.  Обязательный вывод `[IMP:7-10]` логов в консоль теста (через `caplog` или `print`).

## Приложение Б: Заметки по реализации

### Установка зависимостей
- Установите `openai` (если отсутствует): `pip install "openai>=1.0.0"`
- Остальные библиотеки уже присутствуют в системе: `pytest`, `logging` (stdlib).

### Работа с OpenAI SDK
- Используйте библиотеку `openai` версии >= 1.0.0.
- Для кастомного `base_url`: `client = openai.OpenAI(base_url=..., api_key=...)`.
- **Важно:** клиент не должен сохранять API key в какие-либо файлы.

### Мокирование HTTP в тестах
- Используйте `unittest.mock.patch` на уровне `openai.OpenAI.chat.completions.create`.
- Пакет `responses` не установлен и не должен использоваться.

### Получение API key (цепочка fallback)
1. Аргумент командной строки: `--api-key <KEY>` (наивысший приоритет).
2. Переменная окружения: `OPENROUTER_API_KEY`.
3. Переменная окружения: `LLM_API_KEY`.
4. Если ни один источник не предоставил ключ — `sys.exit(1)` с сообщением: `"API key is required. Provide via --api-key or OPENROUTER_API_KEY environment variable."`

### Установка переменной окружения (PowerShell)
Перед запуском `run_mvp.py` установите переменную в том же терминале:
```powershell
$env:OPENROUTER_API_KEY="sk-or-v1-..."
```
Ключ действует до закрытия терминала. **Не пишите ключ в чат с AI-агентом.**

### API key security (защита от случайного коммита)
- **CRITICAL:** API key НИКОГДА не должен быть записан ни в один файл внутри `lesson_X/`.
- Не создавайте `.env` файлы внутри `lesson_X/`.
- Не пишите ключ в `config.json`.
- Не логируйте ключ (даже частично) в `app_X.log`.
- Текущий `.gitignore` уже игнорирует `*.log`, `__pycache__/`, `.env`, `venv/` — этого достаточно.

### Поддерживаемые бэкенды
- **DeepSeek API** (основной): `base_url = "https://api.deepseek.com"`, API-ключ вида `sk-...`.
- **LM Studio** (локальный): `base_url = "http://localhost:1234/v1"`, ключ не требуется.
